# Spectral Frequency 1.0 Stabilization Ledger

This document is the authoritative internal history of pre-release 1.0 implementation work.

## Status vocabulary

- **Planned** — accepted direction, not yet implemented
- **Implemented** — files supplied or committed
- **Parses successfully** — no relevant load/parser errors observed
- **In-game tested** — directly exercised in Minecraft
- **Regression passed** — relevant earlier workflows were retested
- **Release approved** — accepted for the public 1.0 build
- **Deferred** — intentionally moved out of the current release scope
- **Superseded** — replaced by a later ledger entry

No system should be considered release-complete merely because it parses.

## SF10-FIX-013 — Resilient 30-second scheduler

**Status:** In-game tested  
**Release target:** 1.0  
**Area:** Scheduler, Memory pressure, diagnostics

### Problem

The 30-second heartbeat refreshed once after enabling and then became stale because gameplay logic could prevent reliable re-arming.

### Resolution

- Split the scheduler into a wrapper and worker.
- The wrapper schedules its next execution before running gameplay logic.
- Runtime startup arms the wrapper after one tick.
- Environmental Memory pressure and UV cleanup remain in the worker.

### Verification

The heartbeat continued advancing across multiple 30-second intervals and the health report returned `HEALTHY`.

## SF10-STAB-014 — Guarded full purge and clean reinstall

**Status:** In-game tested; destructive regression pending  
**Release target:** 1.0  
**Area:** Administration, permanent cleanup, reinstall, offline recovery

### Changes

- Added a two-step permanent-data purge requiring an explicit request and confirmation.
- Added a thirty-second confirmation timeout.
- Added a cancellation command that leaves runtime data untouched.
- Preserves player-owned Spectral Frequency equipment by default.
- Added a separate explicit equipment-removal option.
- Removes online-player progression, advancements, identity tags, loaded runtime entities, scoreboards, bossbars, and known storage records.
- Leaves a schema-zero purge tombstone so `/reload` cannot silently reinstall the datapack.
- Added an explicit clean reinstall path that rebuilds schema 100.
- Added returning-player cleanup for stale tags, advancements, and optionally retained Spectral Frequency equipment.
- Preserved the existing nondestructive soft-uninstall and enable workflow.

### Commands

- `/function sf:core/purge/request`
- `/function sf:core/purge/cancel`
- `/function sf:core/purge/gear`
- `/function sf:core/purge/confirm`
- `/function sf:core/reinstall`

### Verification completed

- `/reload` produced no relevant function errors.
- `/function sf:dev/health` remained healthy.
- Purge request armed successfully.
- Purge cancellation disarmed the request without deleting progression.
- The thirty-second timeout disarmed the request.
- Confirmation was rejected after the timeout expired.

### Destructive verification still required

- Actual permanent-data purge
- Objective and bossbar removal
- Storage tombstone behavior across `/reload`
- Clean schema-100 reinstall
- Online-player reinitialization after reinstall
- Optional equipment deletion
- Offline-player cleanup on later reconnect
- Unloaded entity and container limitations

### Migration implications

Existing installations are unaffected unless an administrator deliberately runs both the request and confirmation commands. Soft uninstall remains nondestructive. Full purge intentionally destroys Spectral Frequency progression and requires the explicit reinstall command before normal runtime loading resumes.

### Known limitations

- Entities and dropped items can only be removed while loaded.
- Items stored in containers cannot be discovered globally.
- Optional gear cleanup for offline players is deferred until those players return after reinstall.
- The destructive cycle must be tested in a disposable fixture before release approval.
